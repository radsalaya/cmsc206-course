01

Why Build Logic into the Database?

Traditionally, application programs contain all the business logic. The database stores rows; the code decides what those rows are allowed to be. Moving some of that logic into the database offers several benefits.

Advantage Description
Efficiency Operations run closer to the data, reducing network overhead.
Consistency Rules are enforced the same way for all applications.
Security Sensitive operations can stay within the DBMS.
Reusability The same logic can be reused across projects and users.

Note: Database-side logic can reduce portability between different DBMSs, since the syntax varies from one system to the next.

Points to Remember

  • Trigger = when – if – then
  • BEFORE / AFTER / INSTEAD OF
  • NEW and OLD row references
  • Function returns; procedure acts
  • SQLite: triggers yes, stored routines no

That trade-off is the shape of the whole topic. Every advantage below comes from the logic being closer to the data; the one drawback comes from it being written in a dialect only that DBMS understands.

02

Triggers

Trigger

A trigger is a stored SQL program that runs automatically when a specified event occurs in the database.

It is essentially a when–if–then rule. Tap each part to see what it covers.

Triggers embed monitoring and enforcement logic directly inside the database. Because nothing invokes them explicitly, they hold no matter which application — or which careless script — touches the data.

03

Trigger Syntax

The general form in SQLite:

sqlite

CREATE TRIGGER trigger_name
{ BEFORE | AFTER | INSTEAD OF } { INSERT | UPDATE | DELETE }
ON table_name
[ FOR EACH { ROW | STATEMENT } ]
[ WHEN (condition) ]
BEGIN
   -- action statements
END;

Reading the clauses

For more examples, visit the SQLite Trigger Tutorial.

04

Example: Reducing Stock After an Order

sqlite

CREATE TRIGGER reduce_stock
AFTER INSERT ON OrderHasBook
BEGIN
  UPDATE Book
  SET StockQuantity = StockQuantity - NEW.Quantity
  WHERE ISBN = NEW.ISBN;
END;

Each time a new order item is inserted, this trigger automatically decreases the book’s stock.

The keyword to notice is NEW. Inside the body it refers to the row being inserted, so NEW.Quantity and NEW.ISBN read values from the very row that set the trigger off. For a DELETE trigger the counterpart is OLD; an UPDATE trigger can use both.

This is the kind of rule that would otherwise have to be repeated in every application that writes an order — the web app, the admin panel, the nightly import script. Put it in the database once and none of them can forget it.

Note: SQLite supports triggers but not complex stored procedures or user-defined functions.

05

When to Use Triggers

Use triggers when you need to:

  • Enforce business rules — for example, prevent negative stock levels;
  • Log or audit data changes;
  • Maintain summary or history tables; and
  • Automatically validate or clean data.

Avoid triggers when the logic is easier to maintain or debug in the application layer. A trigger runs invisibly: nothing in the calling code mentions it, so a developer reading that code has no hint it exists.

06

Functions & Stored Routines

While SQLite supports built-in functions such as COUNT(), AVG(), and substr(), and even lets developers define their own functions in application code (in Python or C, for instance), it does not allow creating and storing SQL-based functions inside the database.

To understand how user-defined functions work in other DBMSs, here is an example using PostgreSQL, which supports stored routines written in its procedural language PL/pgSQL:

postgresql · pl/pgsql

CREATE OR REPLACE FUNCTION get_total_sales(publisher_id INT)
RETURNS NUMERIC AS $$
DECLARE
  total NUMERIC;
BEGIN
  SELECT SUM(price * quantity)
  INTO total
  FROM Orders o
  JOIN OrderHasBook ob ON o.OrderID = ob.OrderID
  JOIN Book b ON ob.ISBN = b.ISBN
  WHERE b.PublisherID = publisher_id;
  RETURN total;
END;
$$ LANGUAGE plpgsql;

You can then call the function like this:

postgresql

SELECT get_total_sales(1);

The point of the example is not the syntax but the shape: a named routine, stored in the schema, that takes a parameter, runs a query, and returns a single value — usable anywhere a value is expected.

Note: In SQLite, you would achieve similar logic by calling built-in functions or writing custom ones in the host application code, but not by defining them as stored routines in the database itself.

07

Function vs Procedure

Feature Function Procedure
Returns a value Yes Optional / No
Used inside SELECT Yes No
Can modify data Typically not Yes
Focus Computation Action / Workflow

computation

Function

Returns a value and can be used inside a SELECT. Typically does not modify data — you ask it a question and it answers.

action / workflow

Procedure

May return nothing, cannot be used inside a SELECT, and is expected to modify data. You call it to make something happen.

The dividing line is the same one SQL draws everywhere else: a function belongs to an expression, a procedure belongs to a statement.

08

Languages for Stored Routines

Different database systems support various procedural extensions that let you define and store reusable routines inside the database.

DBMS Procedural language Notes
PostgreSQL PL/pgSQL Full procedural language; supports loops, variables, and conditions.
Oracle PL/SQL Very similar to PL/pgSQL, widely used for enterprise applications.
MySQL SQL/PSM Allows creation of stored procedures and functions using DELIMITER blocks.
SQLite — SQLite does not support stored procedures or persistent user-defined functions written in SQL. However, it provides many built-in functions (e.g. COUNT(), ABS(), strftime()) and lets developers define new functions programmatically in C, Python, or other languages when embedding SQLite in an application.

This table is the portability problem. The same routine written for PostgreSQL will not run on Oracle or MySQL without rewriting, and will not run on SQLite at all.

09

Good Practices

  • Keep triggers and procedures simple and predictable.
  • Document clearly what events or parameters they handle.
  • Avoid circular or recursive triggers.
  • Test thoroughly before deployment.
  • For complex logic, consider implementing it at the application level.

The third one bites hardest. A trigger on Book that itself updates Book is exactly the shape of an infinite loop; some systems detect it, some cap the recursion depth, and some simply run until something breaks.

A useful habit: write down, next to every trigger, the single sentence that says what invariant it protects. If you cannot write that sentence, the logic probably belongs in the application.

Practice Activity: Working with Triggers in SQLite

In this activity you will create your own database and practise writing a trigger in SQLite, using an online SQL playground to execute your commands.

Go to the SQLite online environment: Execute SQL Online — db-book.com. Start with a clean database.

Work through the steps in order.

Create a new database. Paste the script below, then click Execute.

step 1 · schema + data

-- Create tables
CREATE TABLE Book (
    ISBN TEXT PRIMARY KEY,
    Title TEXT NOT NULL,
    Price REAL NOT NULL,
    StockQuantity INTEGER NOT NULL,
    LastUpdated TEXT
);

CREATE TABLE Orders (
    OrderID INTEGER PRIMARY KEY AUTOINCREMENT,
    OrderDate TEXT NOT NULL,
    Customer TEXT
);

CREATE TABLE OrderHasBook (
    OrderID INTEGER,
    ISBN TEXT,
    Quantity INTEGER,
    FOREIGN KEY (OrderID) REFERENCES Orders(OrderID),
    FOREIGN KEY (ISBN) REFERENCES Book(ISBN)
);

-- Insert sample data
INSERT INTO Book VALUES
('978-0-1234', 'Database Systems', 600.00, 25, NULL),
('978-0-5678', 'SQL Fundamentals', 480.00, 18, NULL),
('978-0-9999', 'Advanced Topics in DBMS', 700.00, 12, NULL);

INSERT INTO Orders (OrderDate, Customer)
VALUES ('2025-11-01', 'Ria Borromeo'),
       ('2025-11-03', 'Juan dela Cruz');

INSERT INTO OrderHasBook VALUES
(1, '978-0-1234', 2),
(1, '978-0-5678', 1),
(2, '978-0-9999', 1);

This creates three tables — Book, Orders, and OrderHasBook — with a few sample rows.

Inspect the tables. View the contents of the Book table.

step 2

SELECT * FROM Book;

Notice that the column LastUpdated is currently NULL for all books.

Create a trigger that automatically updates LastUpdated whenever a book’s record is modified — its price or stock, for instance.

step 3

CREATE TRIGGER update_book_timestamp
AFTER UPDATE ON Book
BEGIN
  UPDATE Book
  SET LastUpdated = CURRENT_TIMESTAMP
  WHERE ISBN = NEW.ISBN;
END;

This trigger fires after every UPDATE on the Book table and sets the LastUpdated field to the current time.

Test the trigger. Try updating one of the book records, then check the result.

step 4 · make a change

UPDATE Book
SET Price = Price + 50
WHERE ISBN = '978-0-1234';

step 4 · check the result

SELECT Title, Price, LastUpdated FROM Book;

The LastUpdated value for Database Systems should now show a timestamp indicating when the change was made.

Tip: Triggers are powerful for automating consistency checks and logs. However, use them with care to avoid circular updates or performance overhead.

Summary

  • Moving business logic into the database buys efficiency, consistency, security, and reusability — at the cost of portability, since syntax varies between systems.
  • Triggers automate actions when specific data changes occur. They are when–if–then rules: an event, an optional condition, and an action.
  • A trigger declares BEFORE, AFTER, or INSTEAD OF; the event (INSERT, UPDATE, DELETE); the table; row or statement granularity; and an optional WHEN condition.
  • Inside the body, NEW refers to the incoming row and OLD to the row being replaced or removed.
  • Use triggers to enforce business rules, log or audit changes, maintain summary tables, and validate data. Avoid them when the logic is easier to maintain or debug in the application layer.
  • Stored procedures and functions encapsulate logic for reuse and consistency. A function returns a value and works inside a SELECT; a procedure acts and does not.
  • SQLite supports triggers and built-in or application-defined functions, but does not store SQL-based procedures or user-defined functions inside the schema. PostgreSQL provides PL/pgSQL, Oracle PL/SQL, and MySQL SQL/PSM.
  • Good practice: keep routines simple and predictable, document what they handle, avoid circular or recursive triggers, test thoroughly, and push complex logic up into the application.
