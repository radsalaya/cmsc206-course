02

Database (DB)

Definition

A DB is a collection of related data, facts about a particular world or process, with meaning, a purpose and target users.

  • As you can see, this is a very broad definition…
  • Data takes many forms: numbers, text, images, sounds, video, etc.
  • Note that any random collection of data is not a DB.

03

Database Management Systems

Definition

A DBMS is a software system that enables users to create, maintain, and exploit a database.

It allows users to:

Specify the structure of the database, the data that will be stored, its type and constraints. This constitutes the metadata of our data.

Insert the data in the database and store it durably.

Retrieve and update data from the database.

Allow multiple users to use the database concurrently.

05

DB without DBMS

If a DB is just a coherent collection of data, why do we need a DBMS? Why not just keep our data in files that we format in an ad-hoc way and organise them through the directory tree and filenames?

If we take the example of a university, we have:

  • The student records system works with /school/program/year/student_name_grades.csv files, where each line records a class taken and the grade obtained.
  • The financial office’s system works with /school/program/year/student_name_fees.csv files, where each line records a transaction on the account of the student.
  • The PR system works with /school/program/year.csv files, where each line records a student name and their contact info.

Drawbacks of storing data using a filesystem

Data redundancy

student_name appeared in three (3) different places. We are wasting storage.

Risk of inconsistency

What happens if one person is recorded as Thomas in the student records and Tomas in the financial system? What happens if my PC crashes while I am modifying a file?

No concurrency control

What happens if two people modify fees records at the same time? Will one’s modification override someone else’s?

Low flexibility

The format of the data cannot be easily changed. We can only use ad-hoc programs to process the data as there are no standard formats.

06

We want ACID

What we are missing, and that a DBMS provides to different degrees, is the ACID properties. Tap a letter to read it in full.

But BASE works in some cases too

Strict consistency and reliability — the guarantee you want when the data is money.

  • Atomicity — all or nothing.
  • Consistency — valid state to valid state.
  • Isolation — concurrent transactions don’t interfere.
  • Durability — committed stays committed.

Typical use: banking.

BASE is an alternative to ACID, common in NoSQL databases (e.g. MongoDB, Cassandra, DynamoDB).

  • Basically Available — the system guarantees availability, but may return stale data.
  • Soft state — the state of the system may change over time, even without new input, due to replication and background processes.
  • Eventual consistency — the system will become consistent if given enough time, though temporary inconsistencies are allowed.

Typical use: e-commerce, social media — speed, scalability, high availability.

07

Abstraction through the DBMS

To allow us to achieve ACID properties, the DBMS provides different abstractions. There are three levels of abstraction, which should work independently — we could change the way we implement one level without impacting the others.

View level

The details of the data types are hidden. Different views are created depending on your accessible data. Your boss may view your salary but you may not view his, for example.

Who cares: the end user, who is just interested in browsing the data.

View level

Two users can look at the same database through completely different windows. Each view exposes only the data that user is allowed to see.

Who cares: the end user, who is just interested in browsing the data.

Logical / Conceptual level

We ask: what data is being stored? What is the type of the data? How are different data items related — e.g. the ”lecturer” item in the record for a class must be a ”person” record? Who can access what part of the data?

Who cares: the programmer building something on top of the DB.

Physical level

How the data is stored on disk. Here we consider file formats, encoding, and so on. This is usually handled 100% by the DBMS.

Who cares: the DBMS administrator, interested in how files are saved to disk.

Each level is a higher-level abstraction of the data, and each is of concern to different people. The DBMS administrator is interested in how the files are saved to disk. A programmer building something on top of the DB is interested in the data types but not in how the data is actually stored. The end user is just interested in browsing the data.

08

Types of DBMS

Focus of this course

Relational (RDBMS)

Data is very structured into tables and columns with strong constraints on them. ACID properties are strongly enforced.

Object oriented (OODB)

Simplifies the interaction between object-oriented programming languages and relational databases. Objects can be saved into and retrieved directly from the DB.

NoSQL

Emerged with Big Data. Much faster than RDBMS but ACID is sometimes relaxed. E.g. key/value stores, column stores, document stores, graph databases.

—

Summary

  • A Database (DB) is a structured collection of related data with meaning and purpose.
  • A Database Management System (DBMS) lets us define, construct, manipulate, and share data.
  • Managing data through plain files leads to redundancy, inconsistency, and lack of concurrency control.
  • ACID properties ensure reliability in traditional databases: Atomicity, Consistency, Isolation, Durability.
  • BASE properties (in many NoSQL systems) trade strict consistency for availability and scalability.
  • A DBMS provides three levels of abstraction: physical, logical, and view levels.
  • Types of DBMS include Relational (RDBMS), Object-Oriented, and NoSQL.
