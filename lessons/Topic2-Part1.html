Before you write a single CREATE TABLE statement, you need a way to plan your database, foresee the problems that would otherwise cost you hours of rework, and communicate the design to other DB admins, the programmers who will use it, and the product owners who wrote the requirements. That's what a data model gives you.

In this lesson, we'll build up the Entity-Relationship (ER) model piece by piece — entities, attributes, relationships, keys — and the notation used to draw it. Part 2 picks up from here and converts an ER diagram into an actual relational schema.

By the end of this lesson, you should be able to

  • identify and define entities, attributes, relationships, and keys in a given scenario;
  • draw a basic Entity-Relationship Diagram (ERD) using standard notation;
  • interpret ER diagrams and explain common cardinality and participation rules; and
  • convert an ER diagram into a relational schema — this last one is Part 2's job; Part 1 gets you everything leading up to it.

Estimated study time: 45–60 minutes.

Page 1

Why We Use Data Models

A data model is a formal way to describe how data is organized, structured, and related within a system or organization. It's a blueprint for how information is represented, connected, and managed in a database.

  • Describes entities (objects or concepts), their attributes (properties), and the relationships between them.
  • Sets the foundation for designing databases that are clear, consistent, and aligned with real-world needs.
  • Standardizes the way data is stored and shared — promoting accuracy and reducing redundancy.
Data modeling answers
  1. What data do we store?
  2. How are different pieces of data related?
  3. What rules or constraints apply to our data?
Skipping the model doesn't skip the design work — it just means you do it later, in production, the expensive way.

Three Levels of Data Model

The same database can be described at three different levels of detail — each one hiding a different set of implementation concerns from the level above it.

Conceptual

  • Close to how people naturally perceive data.
  • Focuses on what matters — the big picture of entities and relationships.
  • Avoids technical or implementation detail entirely.
Example: the Entity-Relationship (ER) model.

Logical

  • Still understandable to people, but closer to how data actually sits in the computer.
  • Adds attributes, keys, and precise relationships.
  • Still independent of any specific DBMS or physical storage.
Examples: Relational, Network, Hierarchical models.

Physical

  • Specifies how data will actually be stored and managed.
  • File structures, indexing, data types — specific to a DBMS platform.
Examples: SQL-specific tables, indexes, partitions, storage locations.

The Entity-Relationship Model

The ER model was developed by Peter Chen in 1976 to provide a simple, understandable way to represent the structure and logic of a database — identifying which entities belong in it and how those entities relate to each other.

It's built from just two elements:

ENTITIES
RELATIONSHIPS

Entities are the real-world objects or concepts represented in the database. Relationships are the associations or interactions between them. (Attributes, the third piece of the triad above, describe the entities themselves — more on those in Page 5.)

Chen, Peter Pin-Shan. "The entity-relationship model—toward a unified view of data." ACM Transactions on Database Systems (TODS) 1.1 (1976): 9-36.

Definitions

Entity
An object with a physical existence — a particular person, car, house, or employee — or a conceptual existence, like a company, a job, or a university course.
Entity set
A collection or group of entities that share the same properties or attributes in a database or data model.
Attributes
The properties that define the entity type — the data that needs to be stored for each entity. In a database table, attributes are the columns.
Page 6

Types of Entities

Strong entity (independent entity) — can be uniquely identified by its own attributes, without depending on any other entity. It has a primary key sufficient on its own.

Example
Entity: Student  ·  Attributes: Student_NO (primary key), Name, Date_of_Birth
Student_NO alone uniquely identifies each student — so Student is a strong entity.

Weak entity — cannot be uniquely identified by its own attributes alone. It depends on a strong entity (its owner or identifying entity) for its existence, and has only a partial key.

Example
Entity: Enrollment (records a student's enrollment in a course)  ·  Attributes: Enrollment_no (partial key), Course_ID, Grade
There can be no Enrollment without a Student. The unique identifier for a record is Enrollment_no combined with Student_ID.

Choosing Attributes of Entities

An entity's attribute must:

  • Be directly linked to the entity.
  • Not be influenced by time — store birthdate, not age.
  • Not be influenced by other entities — number of siblings shouldn't be an attribute if it can be counted from the database instead.
  • Avoid data redundancy.
If you can compute it from something else already in the database, don't store it separately.
Check your understanding
Which of these should NOT be stored as an attribute of an Employee entity?
Hire_Date is fine — it's a fact about the employee that doesn't change and isn't derivable from anything else.
Correct. This is exactly the Age/Date_of_Birth problem again — Years_of_Service changes with time and can be derived from Hire_Date, so storing it directly violates the "not influenced by time" rule and invites redundancy.
Employee_ID is a fine attribute — likely the key attribute, in fact.

Types of Keys

  1. Primary key — a unique identifier for each record in a table. No two rows share it, and it can never be NULL.
    Example: in a Student table, Student_ID.
  2. Candidate key — any attribute (or set of attributes) that could qualify as the primary key. There can be several; only one gets chosen.
    Example: Student_ID and Student_Email might both be unique — both are candidate keys, even though only one becomes primary.
  3. Composite key — two or more attributes that together uniquely identify a record, used when no single attribute is enough.
    Example: in an Enrollment table, neither Student_ID nor Course_ID alone is unique — together, they are.
  4. Foreign key — an attribute in one table that links to the primary key of another, establishing the relationship between the two tables.
    Example: Enrollment.Student_ID references Student.Student_ID, ensuring every enrollment corresponds to a real student.
Check your understanding
In a Book table, both ISBN and Book_Code are independently unique for every row, but ISBN was chosen as the one the DBMS enforces. What is Book_Code now?
Correct. It still uniquely identifies each record — it simply wasn't the one selected as primary. Every primary key started out as a candidate key; the others don't stop qualifying just because they weren't picked.
Not quite — a foreign key points to another table's primary key. Book_Code lives in the same table and identifies the same record ISBN does, so this isn't that relationship.
Not quite — it's just as capable of uniquely identifying a row as ISBN is. "Not chosen" isn't the same as "not valid."

In that same style of Course_Offering table (linking Course and Semester), Course_ID also exists purely to point back to the Course table's own primary key. What role is Course_ID playing here?
Not on its own — a composite key is Course_ID combined with another column to form one shared identifier. Pointing back to another table's primary key is a different job.
Correct. Course_ID here links this table back to the primary key of the Course table — the definition of a foreign key.

A car has exactly one registered engine, identified by serial number, and that engine belongs to exactly one car. What's the cardinality between Car and Engine?

Participation Constraint

Total participation — every entity in the set must participate in the relationship. Shown as a double line.

Partial participation — an entity in the set may or may not participate. Shown as a single line.

If every student must enroll in a course, Student's participation is total. If some courses have no students enrolled yet, Course's participation in that same relationship is partial.

How to Draw an ER Diagram

1 · IDENTIFY ENTITIES
↓
2 · IDENTIFY RELATIONSHIPS
↓
3 · ADD ATTRIBUTES
↓
4 · ASSIGN CARDINALITY & PARTICIPATION
↓
5 · REVIEW & REFINE

1 · Identify all the entities

  • Analyze the domain to find every distinct object or concept (e.g., Student, Course, Department).
  • Represent each entity as a rectangle.
  • Keep entity names clear, concise, and meaningful.

2 · Identify the relationships between entities

  • Determine how entities interact (e.g., Student enrolls in Course).
  • Represent each relationship as a diamond between the related entities.
  • Label each relationship with a verb phrase.
  • Never connect a relationship directly to another relationship — only to entities.

3 · Add attributes to entities and relationships

  • Represent attributes as ovals connected by straight lines.
  • Underline key attributes.
  • Mark multivalued, derived, and composite attributes with their proper notation.

4 · Assign cardinality and participation constraints

  • Specify cardinality (1:1, 1:N, M:N) on each side of a relationship.
  • Indicate total or partial participation with double or single lines.

Check Your Understanding

UngradedTen questions covering this lesson. Not graded — just to check where things stand before Part 2.

1
What is a data model, in your own words?
A formal way to describe how data is organized, structured, and related within a system — a blueprint for how information is represented, connected, and managed in a database.
2
Which level of data model is closest to how data is stored in the computer, yet still independent of any specific DBMS or physical storage?
Conceptual stays at the big-picture level — entities and relationships only, no storage detail at all.
Correct — this is the trickiest distinction in the lesson. Logical models add attributes and keys and resemble computer storage, but they still don't commit to a DBMS or physical layout.
Physical models are explicitly tied to a DBMS platform (file structures, indexes) — the opposite of "independent."
3
In Chen's notation, what does a diamond represent?
Entities are rectangles.
Attributes are ellipses.
Correct — the diamond connects entities to show how they associate with each other.
Weak entities get a double rectangle, not a diamond.
4
An "Insurance_Claim" entity can only exist if tied to a "Policy" entity, and is identified by a partial key. Strong or weak entity?
Not quite — a strong entity is self-sufficient. This one depends entirely on Policy for both existence and identification.
Correct — dependent existence plus a partial key is exactly the definition of a weak entity, with Policy as its owner.
5
"Full_Name" is broken down into First_Name, Middle_Name, and Last_Name. What kind of attribute is Full_Name?
Multivalued means several values of the same kind — like several phone numbers. This is different values of different kinds, combined into one attribute.
Correct — exactly like Address breaking down into Country, ZIP code, City/Province, and Street.
Derived means computed from another attribute, like Age from Date_of_Birth. Full_Name isn't computed — it's composed of parts.
6
What's the difference between a candidate key and a primary key?
A candidate key is any attribute, or set of attributes, that could uniquely identify a record — there can be several in one table. The primary key is whichever candidate key actually gets chosen to do that job. Every primary key is a candidate key; not every candidate key is the primary key.
7
In an Enrollment table linking Student and Course, why is a composite key needed instead of a single-column key?
Neither Student_ID nor Course_ID alone is unique in that table — the same student appears in many rows (one per course), and the same course appears in many rows (one per enrolled student). Only the combination of the two is guaranteed unique per row, which is exactly what a composite key is for.
8
Which example is a unary relationship?
Correct — only one entity type is involved.
That's binary — two entity types.
That's ternary — three entity types.
9
One passport is issued to exactly one citizen, and one citizen holds exactly one passport. What's the cardinality?
Correct — each side is capped at exactly one, same shape as Surgeon and HOD.
One-to-many would mean one citizen could hold several passports, or vice versa — not the case here.
Many-to-one implies many on one side and exactly one on the other — but both sides here are exactly one.
10
What does total participation mean, and how is it shown in an ER diagram?
Total participation means every entity instance in that entity set must take part in the relationship — there's no instance that sits outside it. It's shown with a double line connecting the entity to the relationship diamond, as opposed to a single line for partial participation.
