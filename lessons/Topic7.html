01

Introduction

In previous modules we learned how to write SQL queries. But how does the RDBMS process those queries internally?

This lesson gives a high-level view of what happens after a query is executed:

  • How the query is validated and parsed;
  • How it is optimized to choose the best execution plan; and
  • How SQL can be written in ways that are easier to optimize.

By the end, you will understand how query optimization makes SQL fast and scalable — and why the same result set can take either ten milliseconds or ten seconds depending on a decision you never made yourself.

Points to Remember

  • Validate → parse → optimize → execute
  • SQL is declarative
  • Selection early, projection early
  • Catalog statistics drive cost
  • EXPLAIN QUERY PLAN

02

The Query Lifecycle

When a query is sent to the DBMS, it goes through four main stages.

Tap each stage to see what it does.

SQL query → (parsed + optimized) → query plan → results

Example

SELECT * FROM employees WHERE dept_id = 3;

The DBMS validates the table and column, parses the query, optimizes it, and then executes it using either an index or a sequential scan.

Reflection: why does optimization occur after parsing and not before? Consider what the optimizer needs to work on — you cannot rearrange the pieces of a query until something has broken it into pieces.

03

Validating and Parsing

In the validation and parsing stage, the DBMS:

  • Checks syntax and structure;
  • Verifies that table and column names exist;
  • Ensures data types and functions are valid; and
  • Builds a parse tree — an internal structure representing the query.

Example 1 · a query that passes

example 1 · valid

SELECT city_name FROM City WHERE city_population > 100000;

The parser checks the table and column names and confirms that the WHERE clause is valid.

Example 2 · a query that fails

example 2 · fails validation

SELECT name, salary FROM worker WHERE age = 'thirty';

This query fails validation because of a type mismatch: 'thirty' is not numeric. Notice that nothing here is wrong with the grammar — the failure comes from checking the query against the schema, which is why validation needs the catalog and not just a parser.

04

Optimization Basics

Why an optimizer exists at all

SQL is a declarative language. It specifies what we want, not how to obtain it. The optimizer decides how to execute it efficiently.

A query can have many equivalent plans — all returning exactly the same rows. The optimizer selects the one with the lowest estimated cost.

Example

SELECT * FROM sales WHERE region = 'APAC';
Plan What it does Rows touched
Plan A Sequential scan of all rows, then filter on region 10 M rows
Plan B Index scan using region_idx 10 K rows

The optimizer selects Plan B, because it minimizes I/O and CPU cost. Same answer, a thousandth of the rows touched.

Reflection: what does “cost” mean here? Consider memory usage, disk I/O, and CPU time — and which of the three is usually the one that hurts.

05

Example 1: The Naïve Way

Suppose there are two tables:

Table Schema Size
Country country_id, country_population, country_name 200 rows
City city_id, country_id, city_population, city_name 10,000 rows

And this query:

SELECT City.city_name
FROM City NATURAL JOIN Country
WHERE City.city_population > 100000
  AND Country.country_name = 'France';

The naïve plan

  1. Perform a Cartesian product — 2,000,000 tuples;
  2. Apply the join and WHERE filters;
  3. Project city_name.

This plan produces the correct result, but it creates a large intermediate table, wasting both memory and processing time. Two hundred countries times ten thousand cities is two million rows built in order to throw almost all of them away.

Reflection: which step introduces the most inefficiency, and why? Think about how many of those two million tuples survive the filters.

06

Example 2: A Better Way

The optimized plan

  1. Filter City first (city_population > 100000);
  2. Filter Country (country_name = 'France');
  3. Join the smaller intermediate tables;
  4. Project city_name.

This drastically reduces intermediate results and execution time. Nothing about the answer changes — only the order in which the work is done.

A second example

SELECT e.name, d.dept_name
FROM employees e, departments d
WHERE e.dept_id = d.dept_id AND d.location = 'Manila';
Order of work Result
Join first, then filter Slow — every employee is paired with every department before anything is discarded
Filter departments for 'Manila' first, then join Faster — the join runs against a handful of departments

07

Cost Estimation

The optimizer cannot try every possible query plan — it would take too long. Instead it estimates the cost of each plan using information stored in the database’s catalog statistics.

Statistic What it tells the optimizer
Table size How many tuples a scan would have to read.
Selectivity The value distribution of a column — how many rows a condition is likely to keep.
Indexes and constraints Which access paths are available besides a full scan.

Using these statistics, the optimizer predicts which plan is likely to run the fastest, without actually executing them all. Estimating is the whole point: measuring every candidate would cost more than running the query badly once.

However, outdated statistics can mislead the optimizer. If the catalog still reflects old data distributions, the DBMS might select a plan that scans millions of rows unnecessarily — a query that was fast last month and mysteriously is not today.

In systems such as PostgreSQL, the ANALYZE command refreshes statistics, updating distinct value counts and column histograms to improve cost estimates.

08

Viewing the Query Plan

You can see how the database intends to execute a query with the EXPLAIN QUERY PLAN command in SQLite. It displays the internal steps the optimizer plans to take — whether it will use an index, or perform a full table scan.

EXPLAIN QUERY PLAN
SELECT city_name
FROM City
WHERE city_population > 100000;

This produces output similar to:

output

SCAN TABLE City
SEARCH TABLE City USING INDEX city_population_idx

The result shows whether the optimizer selected an efficient access path. SCAN means every row was read; SEARCH … USING INDEX means it jumped straight to the matching rows. You can test this in the SQLite playground to explore how different queries produce different execution plans.

Note: the wording of the output may vary slightly depending on the SQLite version.

09

Being Nice to Your Optimizer

The optimizer is powerful, but SQL design can help it do better:

  • Avoid using functions on indexed columns, for example UPPER(name);
  • Use consistent data types in joins;
  • Minimize unnecessary subqueries; and
  • Leverage indexes appropriately.

Bad vs good SQL

bad

-- Bad: prevents index use
SELECT * FROM orders
WHERE YEAR(order_date) = 2025;

good

-- Good: index-friendly
SELECT * FROM orders
WHERE order_date BETWEEN '2025-01-01'
                     AND '2025-12-31';

Wrapping the indexed column in a function means the index on order_date can no longer be used — the stored values are dates, but the condition is about something computed from them, and the index knows nothing about that. Rewriting the condition as a range over the raw column puts the index back in play.

Note: an index functions like a book index. It helps the database locate rows quickly without reading the entire table. We will learn how indexes are structured and maintained in the next lesson, Storage, Indexing, and Recovery.

Step 2 · Write it, then optimize it

Write a query that lists city names for cities in France with a population above 100,000 — your own way first. Then think about how you could rewrite it to handle less data before the join.

Try both yourself before switching tabs. Reading the answer is not the exercise.

Hint: think about how you might join the two tables and apply the conditions — and, for the second version, about which rows you could throw away before the join rather than after it.

Switch tabs only once you have run something of your own.

-- Naïve query plan
SELECT City.city_name
FROM City NATURAL JOIN Country
WHERE City.city_population > 100000
  AND Country.country_name = 'France';

One possible naïve version: join everything, then filter.

-- Optimized query plan
-- Step 1: filter cities
CREATE TEMP VIEW T1 AS
SELECT city_id, country_id, city_name
FROM City
WHERE city_population > 100000;

-- Step 2: filter countries
CREATE TEMP VIEW T2 AS
SELECT country_id
FROM Country
WHERE country_name = 'France';

-- Step 3: join results
SELECT city_name
FROM T1 JOIN T2 USING(country_id);

Filter each table down first, then join the two small results.

Step 3 · Compare the plans

Compare their execution plans with EXPLAIN QUERY PLAN. This shows the steps SQLite’s optimizer decided to take.

EXPLAIN QUERY PLAN
SELECT City.city_name
FROM City NATURAL JOIN Country
WHERE City.city_population > 100000
  AND Country.country_name = 'France';

EXPLAIN QUERY PLAN
SELECT city_name
FROM T1 JOIN T2 USING(country_id);

Look for keywords like SCAN or SEARCH USING INDEX to identify whether SQLite used an index or scanned the entire table.

On four cities and two countries the timings will be identical — the dataset is far too small for the difference to show. What you are reading is the shape of the plan. Imagine the same two shapes over the ten thousand cities from Example 1.

Summary

  • Validation and parsing — the DBMS verifies that the query is syntactically correct and that all referenced tables, columns, and data types exist, then builds a parse tree.
  • Translation and optimization — the query is transformed into an internal representation, and the optimizer selects the most efficient execution plan based on estimated costs.
  • Execution — the DBMS carries out the selected plan and returns the requested data.
  • SQL is declarative: you state what you want, and the optimizer chooses how. Many plans return the same rows; the cheapest estimated one wins.
  • The optimizer uses both heuristic rules — selection early, projection early, most restrictive joins first — and cost-based decisions drawn from catalog statistics.
  • Catalog statistics such as table sizes, value distributions, and available indexes inform those cost estimates. Outdated statistics mislead the optimizer; ANALYZE refreshes them in PostgreSQL.
  • Writing SQL that enables early filtering, selective joins, and index use can significantly improve performance.
  • Wrapping an indexed column in a function prevents the index from being used. Rewriting the condition as a range over the raw column restores it.
  • EXPLAIN QUERY PLAN lets you examine the optimizer’s chosen strategy — look for SCAN versus SEARCH … USING INDEX.
