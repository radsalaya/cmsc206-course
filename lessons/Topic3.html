01

Introduction

We now have the tools to design databases — the ER model, the relational model, keys and constraints. But how do we make sure the database we end up with is actually usable: easy to maintain and easy to query? Until now we have mostly been using common sense.

Normalization

Normalization is the process of transforming a relational model into another equivalent model that follows a set of rules that make it avoid redundancy, and thus make it easier to maintain and query.

The rules of normalization rely on the concept of functional dependencies, which we build up in this lesson. First, though, let’s look at a database that is not normalized, to get a feel for why we would want to normalize at all.

Learning outcomes

  • Define functional dependencies and their role in normalization;
  • Identify problems in unnormalized relations;
  • Transform relations into 1NF, 2NF, 3NF, and BCNF; and
  • Explain lossless decomposition.

Points to Remember

  • Update, insertion, deletion anomalies
  • Functional dependency X → Y
  • Determinant and candidate key
  • 1NF, 2NF, 3NF, BCNF
  • Lossless decomposition

A Non-Normalized Schema

A supplier delivers a product in a given quantity. One obvious way to store that is a single table:

Delivery(SupplierId, SupplierTown, ProductID, ProductType, Quantity)

Underlined attributes form the primary key.

Where the redundancy is

  • SupplierTown is repeated for every delivery made by the same supplier.
  • ProductType is repeated for every delivery of the same product.

This is not merely wasted space. It causes anomalies — situations where an ordinary operation on the table either forces extra work or destroys information.

03

Functional Dependencies

To fix anomalies we first need to understand how attributes depend on each other. An FD shows how attributes are related: if we know the value of one attribute (or set of attributes), we can determine another.

Formal definition

A functional dependency is a constraint between two sets of attributes X and Y. We say Y is functionally dependent on X, written X → Y, if:

∀t1, t2 :   t1[X] = t2[X]  ⇒  t1[Y] = t2[Y]

In simpler words: if two tuples have the same value of X, then they must also have the same value of Y. Basically, knowing X gives us Y.

The FDs hiding in the Delivery table

Tap a dependency to see the rule it encodes.

These FDs capture the “rules” in the data that help us remove redundancy. They are what guides the whole process of normalization.

04

Trivial & Non-Trivial FDs

Suppose the Delivery relation also carries a DeliveryId. Not every dependency you can write down is worth anything.

1 · Trivial FD

{DeliveryId} → {DeliveryId, SupplierId, SupplierTown, ProductId, ProductType, Quantity}

This one is trivial because everything on the left is already included on the right. It tells us nothing new.

2 · Non-trivial FDs (the useful ones)

A supplier has only one town. This is a direct FD — it comes straight from a business rule.

Each delivery corresponds to one product.

A product has only one type.

This one follows transitively: DeliveryId → ProductId and ProductId → ProductType, so DeliveryId → ProductType. It is derived, not declared.

NOTE: Some FDs are direct (given by business rules), others are derived (through transitivity). Transitivity is exactly the mechanism that 3NF will later ask us to remove.

05

Remarks & Key Terms

  • FDs are part of the semantics of the data — the meaning of the attributes.
  • They are declared by the database designer and not “discovered” automatically.
  • They are independent of the DBMS itself, though constraints like keys enforce them.
  • FDs depend on the schema, not on a particular state of the database.
  • You cannot always infer FDs just by looking at the current tuples. You need domain knowledge.

That last point matters in practice. Two rows happening to agree today does not make a dependency — only a rule that must hold for every possible state of the table does.

Three terms to keep straight

left-hand side

Determinant

The set of attributes that, when known, uniquely determine the values of the dependent set. If two rows agree on the determinant, they must agree on the dependent attributes.

right-hand side

Dependent set

The attributes whose values are fixed once the determinant is known. In SupplierId → SupplierTown, SupplierTown is the dependent attribute.

special case

Candidate key

A special determinant that determines all attributes of a relation. Every candidate key is a determinant; not every determinant is a candidate key — which is the whole point of BCNF.

Although not part of the core relational model, FDs are essential for query optimization and database schema normalization.

06

From FDs to Normal Forms

  • Functional dependencies (FDs) show how attributes relate.
  • If a schema ignores these dependencies, there could be redundancy and anomalies.
  • Normalization uses FDs to refine schemas and avoid these problems.

Normal forms are the rules we apply during this process.

  • Normal forms = design rules for good database schemas.
  • Each normal form is stricter than the previous one — a relation in 3NF is automatically in 2NF and 1NF.
  • In this lesson we study 1NF, 2NF, 3NF, and BCNF.

NOTE: In practice, not every database follows them strictly. But aiming for 3NF/BCNF makes systems easier to maintain.

The ladder

Tap a level to see what it demands.

First Normal Form

Every value is atomic

No sets, no repeating groups, no multi-valued cells. Columns have consistent domains and unique names, and the order of rows and columns carries no meaning.

Second Normal Form

No partial dependency

In 1NF, and no non-prime attribute depends on only part of a composite key. A relation with a single-attribute key is automatically in 2NF.

Third Normal Form

No transitive dependency

In 2NF, and no non-prime attribute is transitively dependent on the primary key. If A → B and B → C, then C hanging off A is what gets removed.

Boyce–Codd Normal Form

Every determinant is a candidate key

The strictest of the four. It closes the cases 3NF still allows, where a determinant that is not a candidate key sits on the left of a non-trivial FD.

07

First Normal Form (1NF)

A table is in 1NF if and only if:

  1. All attributes are atomic (single-valued). There should be no sets or repeating groups.
  2. Attribute domains are consistent — the same type for all values in a column.
  3. Each column has a unique name.
  4. The order of rows and columns does not matter.

Example 1 · a multi-valued phone column

Switch between the two states of the STUDENT relation.

STUD_NO STUD_NAME STUD_PHONE STUD_STATE STUD_COUNTRY
1 RAM 9716271721,
9871717178		 HARYANA INDIA
2 RAM 9898297281 PUNJAB INDIA
3 SURESH — PUNJAB INDIA

STUD_PHONE holds two numbers in a single cell for student 1. That cell is not atomic, so the relation is not in 1NF.

STUD_NO STUD_NAME STUD_PHONE STUD_STATE STUD_COUNTRY
1 RAM 9716271721 HARYANA INDIA
1 RAM 9871717178 HARYANA INDIA
2 RAM 9898297281 PUNJAB INDIA
3 SURESH — PUNJAB INDIA

The multi-valued attribute is split across rows. Nothing was lost — student 1 simply now has one row per phone number.

Example 2 · a multi-valued course column

Courses is multi-valued, so this is not in 1NF.

ID   Name   Courses
------------------
1    A      c1, c2
2    E      c3
3    M      c2, c3

One course per row — no multi-valued attributes, so this is in 1NF.

ID   Name   Course
------------------
1    A      c1
1    A      c2
2    E      c3
3    M      c2
3    M      c3

NOTE: A database design is considered bad if it is not even in the First Normal Form.

08

Second Normal Form (2NF)

  • 2NF is based on the idea of full functional dependency.
  • It applies to relations with composite keys — relations whose primary key is composed of two or more attributes.
  • A relation with a single-attribute key is automatically in 2NF.

2NF

A relation is in 2NF if it is already in 1NF, and it has no partial dependency — no non-prime attribute depends on just part of a composite key.

Prime vs non-prime

  • Prime attribute — part of some candidate key
  • Non-prime attribute — part of none
  • 2NF only ever complains about non-prime attributes

Example 1 · course fees

STUD_NO COURSE_NO COURSE_FEE
1 C1 1000
2 C2 1500
1 C4 2000
4 C3 1000
4 C1 1000
2 C5 2000

Note that many courses have the same course fee. Tap each observation to see what it rules out.

Fee 1000 appears against C1, C3, and C1 again — so knowing the fee tells you nothing about which course or which student.

Student 4 has two rows at fee 1000, one for C3 and one for C1. The pair does not identify a course.

C1 at fee 1000 belongs to both student 1 and student 4.

Hence COURSE_FEE is a non-prime attribute: it does not belong to the one and only candidate key {STUD_NO, COURSE_NO}.

However, COURSE_NO → COURSE_FEE. COURSE_FEE is dependent on COURSE_NO, which is a proper subset of the candidate key. A non-prime attribute depending on a proper subset of the candidate key is a partial dependency — so this relation is not in 2NF.

To convert it to 2NF we split the table in two:

Table 1

STUD_NO COURSE_NO
1 C1
2 C2
1 C4
4 C3
4 C1
2 C5

Table 2

COURSE_NO COURSE_FEE
C1 1000
C2 1500
C3 1000
C4 2000
C5 2000

Example 2 · when there is nothing to fix

Consider the following functional dependencies in relation R (A, B, C, D):

AB -> C   [A and B together determine C]
BC -> D   [B and C together determine D]

In this relation, AB is the only candidate key and there is no partial dependency — any proper subset of AB (that is, A alone or B alone) does not determine any non-prime attribute. The relation is already in 2NF.

09

Third Normal Form (3NF)

A relation is in 3NF if there is no transitive dependency for non-prime attributes, as well as it being in the second normal form.

Equivalently, a relation is in 3NF if at least one of the following conditions holds in every non-trivial functional dependency X → Y:

  1. X is a super key, or
  2. Y is a prime attribute — each element of Y is part of some candidate key.

In other words

A relation that is in First and Second Normal Form, and in which no non-primary-key attribute is transitively dependent on the primary key, is in Third Normal Form.

NOTE: If A → B and B → C are two FDs, then A → C is called a transitive dependency. Normalizing 2NF relations to 3NF involves the removal of transitive dependencies. If one exists, we remove the transitively dependent attribute(s) from the relation by placing them in a new relation along with a copy of the determinant.

Example 1 · state and country

STUD_NO STUD_NAME STUD_STATE STUD_COUNTRY STUD_AGE
1 RAM HARYANA INDIA 20
2 RAM PUNJAB INDIA 19
3 SURESH PUNJAB INDIA 21

FD set: {STUD_NO → STUD_NAME, STUD_NO → STUD_STATE, STUD_STATE → STUD_COUNTRY, STUD_NO → STUD_AGE}
Candidate key: {STUD_NO}

To convert it into third normal form, we decompose STUDENT (STUD_NO, STUD_NAME, STUD_PHONE, STUD_STATE, STUD_COUNTRY, STUD_AGE) as:

STUDENT (STUD_NO, STUD_NAME, STUD_PHONE, STUD_STATE, STUD_AGE)
STATE_COUNTRY (STATE, COUNTRY)

The determinant, STUD_STATE, stays in both relations — that is what lets us join them back together.

Example 2 · all right-hand sides prime

Consider relation R(A, B, C, D, E):

A  -> BC,
CD -> E,
B  -> D,
E  -> A

All possible candidate keys in the above relation are {A, E, CD, BC}. Every attribute on the right-hand side of a functional dependency is prime, so the second 3NF condition is satisfied everywhere and the relation is in 3NF.

Note: Third Normal Form is considered adequate for normal relational database design, because most 3NF tables are free of insertion, update, and deletion anomalies. Moreover, 3NF always ensures functional-dependency preservation and losslessness.

10

Boyce–Codd Normal Form (BCNF)

The Boyce–Codd Normal Form is based on functional dependencies that take into account all candidate keys in a relation.

BCNF

A relation is in BCNF if and only if every determinant is a candidate key.

To test whether a relation is in BCNF, we identify all the determinants and make sure that they are candidate keys.

Where BCNF differs from 3NF

3NF allows two escapes

X → Y passes if…

X is a super key, or Y is a prime attribute. That second escape is what lets a determinant sit on the left without being a candidate key.

BCNF allows one

X → Y passes only if…

X is a candidate key. The prime-attribute escape is closed, which is exactly why BCNF is stricter than 3NF and why every BCNF relation is also in 3NF.

Because of this, the two forms only ever disagree on relations with more than one candidate key that overlap. For a relation with a single candidate key, 3NF and BCNF ask for the same thing.

12

Normalization & Table Decomposition

You now know what normal forms are, and the examples above have given you an idea of how to transform schemas so that they respect those forms. Every one of those transformations was the same move under a different name.

Decomposition

Decomposition is the process of replacing a relation with a collection of smaller relations.

Decomposition should be lossless. The information in the original relation should be accurately reconstructible from the decomposed relations — otherwise we have traded redundancy for something worse.

Splitting a table is easy. Splitting it so that the join puts it back together exactly — no lost rows, no invented ones — is the part that needs a rule.

13

Lossless Decomposition & Heath’s Theorem

Let R(A1, A2, …, An) be a relation. Let

R1 = π[A1, A2, …, Ai] R,
R2 = π[Ai, …, Aj] R,  …
Rk = π[Al, …, An] R,  …

If R1 * R2 * … * Rk = R, then we say this is a decomposition of R without loss of information. Queries on R and on its decomposition would give the same result.

Heath’s theorem

Heath’s theorem can guide us in table decomposition. It says that if relation R(X, Y, Z) satisfies a functional dependency X → Y, the relation can always be decomposed without loss of information into:

R1 = π[X, Y]
R2 = π[X, Z]

The determinant X appears in both halves. That shared column is what the join uses, and it is why nothing is lost.

Reading the theorem

  • X — the determinant, kept in both
  • Y — what X determines, moved out
  • Z — everything else, stays behind

Worked example

Relation R, where StudentNO plays the role of X, Program the role of Y, and GraduationYR the role of Z:

StudentNO  X Program  Y GraduationYR  Z
2014-12345 BAMS 2019
2012-12346 DCS 2014
2013-12347 MIS 2015

Since StudentNO → Program, we can decompose R as follows, without loss of information:

R1 = π[X, Y]

StudentNO Program
2014-12345 BAMS
2012-12346 DCS
2013-12347 MIS

R2 = π[X, Z]

StudentNO GraduationYR
2014-12345 2019
2012-12346 2014
2013-12347 2015

Join R1 and R2 on StudentNO and you get the original three rows back — no more, no fewer.

Look back at 3NF Example 1 and you will see the same theorem at work: STUD_STATE → STUD_COUNTRY, so STATE_COUNTRY(STATE, COUNTRY) splits off while STATE stays behind in STUDENT.

—

Summary

  • Normalization transforms a relational model into an equivalent one that follows rules which avoid redundancy, making the database easier to maintain and query.
  • Redundancy causes update, insertion, and deletion anomalies — the practical reason normalization exists.
  • A functional dependency X → Y says that if two tuples agree on X they must agree on Y. FDs are declared by the designer from domain knowledge, not discovered from the current rows.
  • The determinant is the left-hand side of an FD; a candidate key is a determinant that determines all attributes of the relation.
  • 1NF: all attributes atomic, consistent domains, unique column names, and row/column order insignificant.
  • 2NF: in 1NF with no partial dependency. Only relations with composite keys can violate it.
  • 3NF: in 2NF with no transitive dependency for non-prime attributes — equivalently, in every non-trivial X → Y, X is a super key or Y is prime.
  • BCNF: every determinant is a candidate key. Stricter than 3NF, which is why every BCNF relation is also in 3NF.
  • Decomposition replaces a relation with smaller ones, and must be lossless: R1 * R2 * … * Rk = R.
  • Heath’s theorem: if R(X, Y, Z) satisfies X → Y, then π[X, Y] and π[X, Z] is always a lossless decomposition.
