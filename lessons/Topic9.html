01

Introduction

This lesson introduces Big Data concepts and shows how data analytics works in practice. You will learn how Big Data differs from traditional DBMS data, and how analysts explore datasets to discover patterns and trends.

Learning outcomes

  • Explain what Big Data means and how it differs from traditional DBMS data — volume, velocity, variety;
  • Name common Big Data tools and describe when they are appropriate;
  • Compare traditional relational DBMS and Big Data systems, and explain when each is suitable;
  • Apply the data analytics lifecycle to a small scenario and identify the right analytics task for each step;
  • Explore data using SQL, label queries as descriptive or diagnostic, and interpret analytical patterns; and
  • Decide when a traditional relational database is enough, and when a Big Data approach is required.

Points to Remember

  • Volume, velocity, variety
  • The SQL does not change
  • Descriptive → prescriptive
  • ACID vs CAP tradeoffs
  • Right tool for the workload

Keep one sentence in view for the whole lesson: Big Data does not replace relational databases. Each system has its strengths, and the real skill is choosing the right tool for the workload.

02

What Is Big Data?

Big Data

Datasets that are too large, too fast, or too varied for a single relational database system to handle efficiently. They often come from logs, IoT sensors, mobile devices, and large-scale user activity.

Big Data is commonly described through the three Vs. Tap each one to see what it does to a traditional database.

Key idea: if one or more of these characteristics apply, a Big Data solution may be more suitable than a traditional relational database. Note the wording — one or more. A dataset does not have to be enormous to need different tools, if it arrives fast enough or messily enough.

03

Big Data vs Traditional DBMS

To decide whether a dataset requires Big Data tools, work through three questions in order. A yes to any one of them is enough.

This is the volume test. It is not about the number that makes a dataset “big” — it is about whether a single machine’s disk and memory can still hold and scan it in a reasonable time.

The velocity test. A modest dataset that grows by thousands of events per second still overwhelms a design built around periodic inserts.

The variety test. Tables, JSON, images, and free text in one pipeline rarely fit a single relational schema without distortion.

If you answer yes to any of these, Big Data tools may be appropriate. If not, a well-indexed relational database is often the best choice — which is the whole of Topic 8 doing its job.

The decision, as a flow

Example: storing a few million sales records is manageable with indexing. Processing millions of event logs per minute from a mobile app is not. The difference is not the word “million” in both sentences — it is per minute.

04

A Big Data Architecture

Big Data systems are built in layers, each solving a different scaling problem. Data arrives, is stored, is processed, and is analyzed — and each layer hands off to the next.

Worked example · a ride-hailing app

Follow one passenger’s booking down through the stack. Tap each layer.

A passenger books a ride. Their phone sends the pickup location, a timestamp, GPS updates throughout the trip, and the payment method. The driver’s app sends status updates and GPS data of its own. One ride is already dozens of events.

Every GPS update and app event goes immediately into a streaming system. This layer absorbs thousands of events per second without losing them — which is exactly what a row-at-a-time INSERT into a single database could not do.

All raw trip data — locations, logs, fares, events — is stored across many machines, which is what makes it possible to keep months or years of trip history rather than only the recent past.

When an analyst asks for the average trip distance per city, the computing framework breaks the work into smaller tasks and runs them in parallel. This keeps queries fast even across billions of rows.

Analysts and data scientists write SQL to answer questions: which hours are busiest, whether fares are rising over time, which locations have high cancellation rates. They reach huge datasets without managing any servers themselves.

Note: SQL itself does not change. What changes is how the system executes your SQL query. A distributed system spreads the work across many machines so that analytics stay fast even when the data is extremely large.

05

Tools and Technologies

Big Data systems combine several tools, each handling one part of the problem. Grouped by what they do:

Job Tools What it solves
Storage Hadoop Distributed File System (HDFS), Amazon S3 Keeping more data than one machine’s disk can hold
Batch processing Hadoop MapReduce, Apache Spark Running a large computation over stored data, in parallel
Stream processing Apache Kafka, Spark Streaming, Apache Flink Handling events as they arrive rather than after the fact
NoSQL databases MongoDB, Cassandra, Redis, Neo4j Storing data whose shape does not suit a fixed relational schema
Cloud analytics Google BigQuery, AWS Athena, Databricks Querying huge datasets without running any servers yourself

The names change every few years; the five jobs do not. When you meet an unfamiliar tool, the useful question is which of these rows it belongs to — and most of the time, that is enough to understand it.

Reminder: Big Data tools are often needed only when data size or speed exceed what a single machine can handle. Reaching for them earlier buys complexity you do not need.

06

How SQL Scales in Big Data Systems

The SQL you have learned in this course continues to be useful even when data becomes very large. Big Data systems still rely on SQL to express analytical queries. What changes is how the system executes the work.

In a relational database (SQLite) In a Big Data environment
All data and processing happen on one machine. The data is distributed across many machines.
The query runs as a single plan on that machine. The system divides the query into smaller tasks and processes them in parallel.
Performance is bounded by one machine’s disk, memory, and CPU. Performance scales by adding machines rather than by buying a bigger one.
The SQL syntax you have learned all term. The same SQL syntax. What changes is performance and scale, not logic.

This connects straight back to Topic 7. There, the optimizer chose between a scan and an index on one machine. Here, the planner makes the same kind of decision across a cluster: which machine holds which partition, what can run in parallel, and when results must be brought back together.

This is why learning SQL well is still valuable. The same ideas apply whether the data is stored on one machine or across a large distributed system — the syntax remains similar, and what changes is performance and scale, not logic.

07

Types of Data Analytics

Analytics helps us understand data and make decisions. Four types are commonly used, and they form a ladder — each one harder than the last, and each one worth more.

Type Question it answers Typical output
Descriptive What happened? Counts, averages, frequency patterns
Diagnostic Why did it happen? Comparisons and drill-downs
Predictive What may happen next? Forecasts, regression models
Prescriptive What should we do? Recommendations, rule-based decisions

Tip: many SQL queries you already know are examples of descriptive and diagnostic analytics. You have been doing the first two rungs of this ladder since Topic 5 without calling them by these names.

08

The Data Analytics Lifecycle

The analytics lifecycle shows the flow of activities involved in turning raw data into insights. Each step has a specific purpose, and the steps often loop back as new questions arise.

Define the question or goal. What decision needs support? An analysis that cannot name the decision it serves will produce numbers nobody uses.

Gather data from logs, APIs, databases, or uploaded files — wherever the evidence for that question actually lives.

Fix missing values, formats, errors, duplicates, and noise. Unglamorous, and usually the largest share of the work.

Look for patterns, outliers, distributions, and trends — before committing to any particular answer. This is what the hands-on activity below is.

Use queries or models to answer the question that step 1 defined.

Summarize the findings and explain what the results mean. A result nobody can act on has not finished the lifecycle — and the explanation often raises a new question, which sends you back to step 1.

Note: this lesson focuses on steps 3 to 5, because these are the core skills you will practise most often when exploring and analyzing data using SQL.

09

Hands-on Activity: Exploring Patterns with SQL

This activity demonstrates how analysts explore a dataset using SQL. You will run summary queries, identify outliers, and look for patterns across time. The dataset has 200 rows, so the patterns are clear and meaningful without being hidden in noise.

Open the SQLite playground: Execute SQL Online.

Step 1 · Load the dataset

First create the Trips table:

CREATE TABLE Trips(
    trip_id INTEGER PRIMARY KEY,
    pickup_time TEXT,
    distance_km REAL,
    fare_amount REAL,
    payment_type TEXT
);

Then load the 200 records. The insert is kept behind a toggle so the page stays readable — switch to it, copy it, and run it.

The insert is one recursive CTE that generates 200 trips — rush-hour clusters in the morning and evening, a late-night bump, four payment types in uneven proportions, and a handful of very short trips.

Switch tabs when you are ready to copy it.

step 1 · 200 generated trips

WITH RECURSIVE seq(i) AS (
    SELECT 1 UNION ALL SELECT i+1 FROM seq WHERE i < 200
),
calc AS (
    SELECT
        i,
        printf('2025-03-%02d %02d:%02d:00',
               (i % 28) + 1,
               CASE
                   WHEN i % 10 IN (0,1,2) THEN 7  + (i % 3)
                   WHEN i % 10 IN (3,4,5) THEN 17 + (i % 3)
                   WHEN i % 10 IN (6,7)   THEN 12 + (i % 2)
                   WHEN i % 10 = 8        THEN 22 + (i % 2)
                   ELSE (i * 7) % 24
               END,
               (i * 13) % 60) AS pickup_time,
        CASE
            WHEN i % 25 = 0 THEN ROUND(0.3 + (i % 7) * 0.1, 1)
            ELSE ROUND(1.5 + ((i * 37) % 220) / 10.0, 1)
        END AS distance_km,
        CASE
            WHEN i % 10 IN (0,1,2)   THEN 'Cash'
            WHEN i % 10 IN (3,4,5,6) THEN 'Card'
            WHEN i % 10 IN (7,8)     THEN 'E-Wallet'
            ELSE 'Voucher'
        END AS payment_type
    FROM seq
)
INSERT INTO Trips (trip_id, pickup_time, distance_km, fare_amount, payment_type)
SELECT i, pickup_time, distance_km,
       ROUND(45 + distance_km * 12 + ((i * 17) % 40), 2),
       payment_type
FROM calc;

Run this immediately after the CREATE TABLE above. It inserts all 200 rows in one statement.

This builds a moderately sized dataset so that summary statistics and patterns become clear — the kind of dataset analysts explore before scaling up to a Big Data environment.

Step 2 · Generate basic summaries

These descriptive queries establish the size and overall distribution of the dataset. Analysts always begin with counts, averages, and category frequencies.

-- How many trips in total?
SELECT COUNT(*) AS total_trips FROM Trips;

-- How are the payment types distributed?
SELECT payment_type, COUNT(*) AS ct
FROM Trips
GROUP BY payment_type;

-- What does a typical trip look like?
SELECT ROUND(AVG(distance_km), 2) AS avg_distance,
       ROUND(AVG(fare_amount), 2) AS avg_fare
FROM Trips;

You should see how many rows exist, how the payment types are distributed, and what a typical journey length and fare look like. These first summaries tell you the shape of the data before you ask anything harder of it.

Step 3 · Identify outliers

Next, check for unusual or extreme values. Outliers can distort averages, and may signal errors, special conditions, or rare patterns worth examining.

SELECT trip_id, distance_km, fare_amount,
       ROUND(fare_amount / distance_km, 2) AS fare_per_km
FROM Trips
WHERE distance_km > 0
ORDER BY fare_per_km DESC
LIMIT 10;

Trips with very short distances produce unusually high fare_per_km values, because a fixed flagdown charge is spread over very little distance. These are natural outliers and appear early in almost every real dataset. What do you observe in the result? Compare the top rows against the typical value and ask whether they are errors, or simply short trips behaving exactly as the pricing rule says they should.

Step 4 · Explore time-based patterns

Many real datasets contain natural cycles — rush hours, peak demand, quiet intervals. Grouping by hour lets you see when activity is highest.

SELECT
    substr(pickup_time, 12, 2) AS hour,
    COUNT(*) AS trips,
    ROUND(AVG(fare_amount), 2) AS avg_fare
FROM Trips
GROUP BY hour
ORDER BY trips DESC;

Times of day with high trip counts may correspond to commute hours or late-night activity. The average fare per hour might show when trips tend to be longer or more expensive. Notice that this query is diagnostic, not merely descriptive: it does not just count trips, it groups them in a way designed to explain when demand happens.

Step 5 · Reflect on scaling up

Now imagine this dataset had 20 million rows instead of 200. Your SQL would be the same, but the performance and infrastructure requirements would not.

  • The logic of the analysis stays the same.
  • The volume becomes too large for a single machine.
  • Distributed systems such as Spark or BigQuery would be required to compute results quickly.
  • The patterns you identified in this smaller dataset still matter at scale.

This is the moment the lesson turns. You should begin to see why Big Data tools exist — SQL does not disappear. The system scales out to handle a much larger dataset, and your query goes with it.

10

Case Study: From a Small Trips Table to a Real System

To understand why Big Data tools exist, it helps to watch a real system grow. We begin with a small ride-hailing dataset much like the one you just used.

Phase 1 · The startup stage

A small transport startup collects a few hundred trip records per day. An analyst uses SQLite on a laptop to compute average fares, busy hours, and the distribution of payment types — precisely the three queries from the activity. Every query runs quickly, because the whole dataset fits in memory.

phase 1

Small Data (fits on one machine)
--------------------------------
  Storage:     single SQLite file
  Processing:  one laptop CPU
  Output:      simple summaries and charts

Phase 2 · Growth and new challenges

After a year the company expands to several cities, and trip volume reaches hundreds of thousands of rides per day. The analyst notices:

  • Queries that used to run in seconds now take minutes;
  • The SQLite file becomes too large to copy easily;
  • Time-based aggregates require scanning millions of rows.

The team migrates to a relational database server with better indexing and more memory. This works for a while, but it will not work forever.

Phase 3 · The system becomes Big Data

The company expands nationwide, and millions of trips are recorded daily. Each trip now carries GPS traces, JSON metadata, text feedback, and device and network logs — all three Vs at once. A single database server can no longer keep up:

  • Daily reports take hours to compute;
  • GROUP BY queries exceed memory limits;
  • Real-time dashboards lag behind actual activity;
  • Storage requirements exceed a single machine.

Phase 4 · Redesigning the architecture

The engineering team adopts tools that answer each of the three Vs directly:

The V What they adopted
Volume Distributed storage such as S3 or HDFS
Velocity Streaming ingestion with Kafka
Variety Flexible formats for structured and semi-structured data

phase 4

Big Data Architecture
---------------------
  Streaming ingest:  Kafka
  Storage:           S3 or HDFS
  Processing:        Spark SQL or Hive
  Analytics:         BigQuery, Databricks

Phase 5 · What the analyst sees

Although every tool beneath them has changed, the analyst still writes a familiar query:

SELECT hour, AVG(fare_amount)
FROM trips
GROUP BY hour;

Key takeaway: SQL does not disappear in Big Data systems. The same query logic applies. Big Data tools simply distribute the work across many machines, so that the same questions can be answered at a much larger scale.

11

Skills, Tradeoffs, and DBMS Connections

What analysts do in Big Data workflows

As data grows, the analyst’s role stays rooted in the same skills you used in the activity. What changes is the scale of the data and the tools needed to process it.

  • Write SQL and analytic queries on very large datasets;
  • Check data quality, inconsistencies, and anomalous values;
  • Summarize patterns across millions or billions of rows;
  • Create automated pipelines that run analyses repeatedly;
  • Collaborate with engineers to access distributed storage and computation.

The core skill remains the ability to reason about data. Every tool on this page will be replaced within a decade; that one will not.

Limitations of Big Data tools

Big Data platforms solve scaling problems, but they introduce new ones.

  • Higher operational complexity and system maintenance;
  • Eventual consistency instead of strict ACID guarantees;
  • Higher storage and compute costs;
  • A need for specialized technical skills;
  • Unnecessary overhead when datasets are small.

Reminder: use Big Data tools only when scale or complexity requires them. For many workloads, a relational DBMS remains the simplest and most effective solution.

Connecting Big Data back to this course

Big Data systems build on ideas from the earlier lessons rather than discarding them.

Idea from earlier In a relational DBMS In a Big Data system
Indexing A single-node index locates rows without a full scan. Data is partitioned across machines and queries run in parallel.
Normalization Normalize for clean design and no redundancy. Pipelines often denormalize — wide tables or JSON — for faster reads.
ACID Strict ACID transactions are the guarantee. Distributed systems take CAP tradeoffs for fault tolerance and scale.

These connections tell you when a traditional DBMS is ideal and when a distributed system becomes necessary — which is the judgment this whole course has been building toward.

Summary

  • Big Data means datasets too large, too fast, or too varied for a single relational system — the three Vs: volume, velocity, variety. Any one of them is reason enough.
  • Decide by asking three questions: is it too large for one machine, is it arriving continuously, does it carry many formats? If none apply, a well-indexed relational database is usually the better choice.
  • A Big Data architecture is layered: sources, a streaming layer (Kafka, Pub/Sub), distributed storage (S3, HDFS), distributed computing (Spark, Hive), and an analytics layer (BigQuery, Databricks). Each layer solves a different scaling problem.
  • SQL itself does not change. What changes is how the system executes it — the work is split into tasks and run in parallel across machines. The syntax stays similar; performance and scale change, not logic.
  • Analytics comes in four kinds: descriptive (what happened), diagnostic (why), predictive (what may happen next), and prescriptive (what to do). Most SQL you already write is the first two.
  • The analytics lifecycle runs from business understanding through collection, cleaning, exploration, modeling, and communication — and loops back as new questions arise.
  • In the activity, descriptive and diagnostic queries revealed the dataset’s shape, its outliers, and its daily cycle. The same queries would answer the same questions at a million times the size.
  • Big Data tools cost something: operational complexity, eventual consistency instead of strict ACID, higher storage and compute bills, specialist skills, and pure overhead on small datasets.
  • They build on this course rather than replacing it — indexing becomes partitioning and parallelism, normalization often gives way to wide tables and JSON, and ACID gives way to the CAP tradeoffs.

Key message: Big Data does not replace relational databases. Each system has strengths. The real skill is choosing the right tool for the workload.
