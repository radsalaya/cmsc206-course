01

Introduction

Once the conceptual design of the database is created using an ER diagram, it must be transformed into a relational model that can be implemented using RDBMS languages such as Oracle SQL, MySQL, and others.

The relational data model describes the world as “a collection of inter-related relations (or tables).”

The relational data model was introduced by E. F. Codd in 1970. Currently, it is the most widely used data model. It has provided the basis for:

  • Research on the theory of data, relationships, and constraints;
  • Numerous database design methodologies;
  • The standard database access language called Structured Query Language (SQL); and
  • Almost all modern commercial database management systems.

02

Relation & Table

Relation

A relation (also called a table or file) is a subset of the Cartesian product of a list of domains, identified by a name.

  • Each row in a table represents a group of related data values and is called a tuple or record.
  • The columns in a table are referred to as fields or attributes.
  • An attribute defines the structure of a record.
  • A record consists of a set of attributes.

The formal logic behind it

The steps below outline the logic between a relation and its domains.

  1. Given n domains, denoted by D1, D2, … Dn.
  2. And r is a relation defined on these domains.
  3. Then r ⊆ D1×D2×…×Dn.

Table

A database is composed of multiple tables, and each table holds the data. A student’s course records and instructor records, for example, live in separate tables that reference each other — not one giant table.

03

Column

  • A database organizes and stores information in a structured manner. Understanding that organization is essential to using it effectively.
  • The main storage units in a database are called columns, fields, or attributes. These fields hold the basic components of data, breaking down information into manageable parts.
  • When creating fields, focus on the common elements of the data, not the specific details that differentiate individual items.

04

Domain

Definition

A domain is the set of atomic (indivisible) values used to model data in a relational model. An atomic value means each value in the domain cannot be further divided.

In summary, a domain defines the acceptable values a column can contain, based on properties and data types.

Records & Fields

Records & fields

Records and fields are the foundation of all databases, allowing data to be stored and linked together for reconstitution. A record (also known as a tuple) contains related fields, such as for a customer or employee. Fields hold individual pieces of data, which together make up a record.

Databases can filter and sort records based on field data, such as dates, which are ordered according to a calendar system rather than as simple numbers.

07

Properties of a Table

  • A table has a name that is distinct from all other tables in the database.
  • There are no duplicate rows; each row is distinct.
  • Entries in columns are atomic. The table does not contain repeating groups or multivalued attributes.
  • Entries from columns are from the same domain, based on their data type — number (numeric, integer, float, smallint…), character (string), date, logical (true or false).
  • Operations combining different data types are disallowed.
  • Each attribute has a distinct name.
  • The sequence of columns is insignificant.
  • The sequence of rows is insignificant.

08

From Logical to Physical Model

When designing a DB, we first draft a conceptual model — the ER model — before designing the physical model with the relational model. This process echoes the levels of abstraction from Part 1.

  1. Design the conceptual model with the end user or stakeholders, who know what information they need but don’t really care about how the DB is implemented.
  2. Make a logical relational model.
  3. Design a physical relational model by adding the domains of the attributes.

This is exactly the three levels from Part 1 — conceptual, logical, and physical — now put into practice.

Notation used below: Table_name(attribute1, attribute2, … attributeN). The underlined attribute is the primary key.

09

Case 1 · Binary, 1:1, Total Participation

A person has 0 or 1 passport number, and a passport is always owned by exactly 1 person.

1. Convert each entity and relationship to tables

  • Person(Per-id) — corresponds to the Person entity, with key Per-Id.
  • Passport(Pass-No) — corresponds to the Passport entity, with key Pass-No.
  • Has(Per-id, Pass-No) — represents the relationship between Person and Passport, taking Per-Id from Person and Pass-No from Passport.

2. Combine tables that can be combined

Since Person and Passport have a 1:1 cardinality with total participation of Passport, we can combine all three into one table.

Person(Per-id, Pass-No)

Each Per-Id will be unique and not null, so it becomes the key. Pass-No can’t be the key, because for some people it can be NULL.

10

Case 2 · Binary, 1:1, Partial on Both Sides

A male marries 0 or 1 female, and vice versa.

1. Convert each entity and relationship to tables

  • Male(M-id)
  • Female(F-id)
  • Marry(M-id, F-id)

2. Combine tables that can be combined

Some males and some females don’t marry. If we merge all three tables into one, whichever column represents the unmarried side would be NULL — but there’s no single attribute we can rely on to always be non-NULL. So we can’t merge all three into one. We convert into two tables instead:

  • Male(M-id, F-id) — the M-id who are married will have an F-id associated. For others, it will be NULL.
  • Female(F-id)

Note: we could just as easily have made Female the table carrying the male attribute if that fit the scenario better — the Female table would then have information on all females.

11

Case 3 · Binary, n:1

Every student can enroll in only one elective course, but an elective course can have more than one student.

1. Convert each entity and relationship to tables

  • Student(S-id)
  • Elective Course(E-id)
  • Enrolls(S-id, E-id)

2. Combine tables that can be combined

  • Student(S-id, E-id)
  • Elective Course(E-id)

Each student needs only one E-id, so Enrolls merges straight into Student — the foreign key sits on the “many” side.

12

Case 4 · Binary, n:m

Every student can enroll in more than one compulsory course, and a compulsory course can have more than one student.

1. Convert each entity and relationship to tables

  • Student(S-id)
  • Compulsory Course(C-id)
  • Enrolls(S-id, C-id)

2. Combine tables that can be combined

None. An n:m relationship can never be merged away — combining any of these would force repeating groups, which breaks the atomic-entries property from Page 7. All three tables stay separate.

13

Case 5 · Relationship with a Weak Entity

An Employee can have many Dependents (one-to-many). A Dependent depends on exactly one Employee for existence.

The Dependent is a weak entity because it cannot be uniquely identified without its related Employee. The Dependent’s key is a combination of the Employee’s primary key (E-id) and a partial key of the Dependent (D-Name). The Dependent’s participation in the relationship with Employee is total.

1. Convert each entity and relationship to tables

  • Employee(E-id)
  • Dependants(D-Name)
  • Has(E-id, D-Name)

2. Combine tables that can be combined

  • Employee(E-id)
  • Dependants(D-Name, E-id)

A weak entity’s relationship to its owner always merges in — there is no Dependant without an Employee, so keeping “Has” as its own table would only ever duplicate the Employee link.

—

Summary

  • The relational model (Codd, 1970) represents data as relations (tables) built from domains.
  • A tuple (record) is a row; an attribute (field) is a column.
  • A domain is the set of atomic values a column may hold; the degree is the number of attributes in a table.
  • A valid table has a distinct name, no duplicate rows, atomic entries, same-domain columns, distinct attribute names, and insignificant row/column order.
  • Converting an ER diagram means turning every entity and relationship into a table, then merging what a cardinality and participation constraint allow you to merge.
  • 1:1 with total participation merges into one table. 1:1 with partial participation on both sides merges into two. n:1 merges the relationship into the “many” side. n:m never merges. A weak entity always absorbs its identifying relationship.
