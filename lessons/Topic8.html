01

Introduction

This lesson explores how a DBMS manages data storage, uses indexing structures to speed up queries, and maintains reliability through recovery mechanisms such as backups, logging, and undo/redo processes.

Topic 7 ended with a promise: an index works like the index of a book, letting the database find rows without reading every page. This lesson opens that up — what an index actually is, what it costs, and what happens to all of it when the machine loses power mid-write.

Learning objectives

  • Describe the differences between storage tiers — RAM, SSD, HDD, tape — and why they matter;
  • Explain how indexes work, and distinguish between B-tree, hash, and composite indexes;
  • Evaluate trade-offs between read performance and write costs when using indexes;
  • Understand database logging, checkpoints, and undo/redo recovery strategies; and
  • Walk through a simple crash recovery example using log entries.

Points to Remember

  • I/O latency is the bottleneck
  • B-tree ranges, hash equality
  • Leftmost-prefix rule
  • Reads gain, writes pay
  • UNDO, REDO, checkpoint

Three ideas carry the whole lesson: storage and indexing choices directly impact database speed; indexes accelerate reads but add overhead to writes; and recovery mechanisms enforce the ACID guarantees, durability above all.

02

Storage Tiers, Costs, and DBMS Buffers

A DBMS interacts with multiple layers of storage, each with different speeds, costs, and durability. Understanding these tiers is essential for understanding query performance.

Tier Character Where it is used
RAM Extremely fast, but volatile Buffers and caches — everything the database wants close at hand
SSD Fast, durable flash storage Common in production systems
HDD Slower, because parts physically move Bulk storage where capacity matters more than latency
Magnetic tape Slow, but extremely cheap per GB Archival backups

Why tiers matter

Most database operations are slowed down by I/O latency. A system that can retrieve more data from RAM, and rely less on disk, will perform better. That single sentence explains nearly every design decision in this lesson.

Key I/O costs

Tap each cost to see where the time goes.

The DBMS buffer manager

The buffer pool caches pages in RAM. When a query needs data, the database first checks the buffer, which is quick. If the page is absent, it loads it from disk, which is slow.

Access path What it reads Best for
Table scan Pages read sequentially, start to finish Large outputs — when you want most of the table anyway
Index lookup A few index pages, then one data page Selective queries — when you want a handful of rows

Note what the second row implies: an index lookup is efficient only for selective queries. Ask for most of the table through an index and you pay a random read per row — worse than simply scanning.

Practice

Which of these reduce the I/O cost of answering a query?

Reflection: think of an application you use that searches through a lot of data — a chat app, email, a messaging client. How would its performance change if it could not cache anything in memory?

03

Indexing Fundamentals

Index

A data structure that allows a DBMS to locate rows quickly without scanning the entire table. Indexes improve read performance but add overhead to writes, so choosing which columns to index matters.

Types of index

Tap each type to see what it is good at.

When to index, and when not to

Index it when… Leave it alone when…
The column is frequently filtered in WHERE clauses The table is small — the overhead outweighs the benefit
The column is used in JOIN conditions The column has low cardinality, unless it is part of a composite key
The column has high cardinality — many distinct values The column is frequently updated in a write-heavy workload
The table is large enough that full scans are expensive —

Creating indexes

-- Index on a single column
CREATE INDEX idx_orders_customer
ON orders(customer_id);

-- Composite index
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);

Indexes accelerate searches but cost storage and maintenance, and composite indexes depend on column order. Too many indexes slow down inserts, updates, and deletes.

Reflection: think of a query you often write. Which column would benefit from indexing, and why?

04

B-trees

B-tree and B+ tree structures are the default indexing method in relational databases. They maintain sorted order, keep the tree height shallow, and support efficient equality and range lookups.

The basics

  • Nodes store keys in sorted order.
  • Tree height stays small even for millions of keys.
  • Leaves contain the actual key–pointer pairs (in a B+ tree).

b+ tree, searching for 70

            [ 50 ]
           /      \
  [10 20 30]    [60 70 80 90]
     leaf            leaf

Search example:
1. Compare key with 50 → go right.
2. Search leaf page containing 60–90.

That shallowness is the whole trick. Each level you descend is one page read, so a tree three or four levels deep finds any row among millions in three or four reads — however the table grows.

Range query support

Because leaf pages are linked in sorted order, B-trees allow efficient scanning of keys within a range — price BETWEEN 100 AND 200. Find the first qualifying key, then walk the leaves sideways until you pass the upper bound.

B-trees are ideal for prefix matches and range queries; hash indexes cannot support ranges at all. Most relational systems rely heavily on B-tree variants for exactly this reason.

Reflection: why do you think B-trees scale so well to extremely large databases? Consider what happens to the height of the tree when the number of keys doubles.

05

Hash Indexes

Hash indexes use a hash function to map key values to buckets. They are extremely efficient for equality lookups, but they do not preserve ordering.

How they work

  • A hash function converts the search key into a bucket address.
  • All keys that hash to the same bucket are stored together.
  • Equality queries resolve quickly by jumping directly to the bucket.

Limitations

no ordering

Ranges are impossible

A hash deliberately scatters nearby values into unrelated buckets. Nothing about the structure says which key comes next, so BETWEEN, <, sorting, and prefix matches are all out.

distribution

Performance depends on spread

If values distribute unevenly across buckets, one bucket grows long and lookups against it degrade. And some systems restrict hash indexes to in-memory structures.

Use hash indexes only when filtering on equality conditions. B-tree indexes are more flexible and more widely supported — which is why they are almost always the right default.

06

Index Maintenance Costs

Indexes accelerate reads but introduce overhead during writes. Every time a row is inserted, updated, or deleted, every relevant index must also be updated.

Cost What it means
Storage Each index requires additional disk space of its own.
Write Inserts, updates, and deletes must all modify every relevant index.
CPU B-tree maintenance — node splits and merges — can be expensive.

Put concretely: a table with no indexes writes rows directly and efficiently. A table with three or more indexes must update each one on every insert — which dramatically slows batch insertion.

This is the trade-off at the centre of the whole topic. An index is not free speed; it is read speed bought with write speed, disk space, and CPU. The question is never “is this index fast?” but “is it worth what it costs?”

07

Practical Indexing Strategies

  • Index only the columns that significantly improve query performance.
  • Use covering indexes when a query can be satisfied directly from the index.
  • Monitor unused indexes and remove them to reduce overhead.
  • For bulk loads, drop the indexes first, load the data, then recreate them — one rebuild beats thousands of incremental updates.

Example · a covering index

SELECT customer_id, total_amount
FROM orders
WHERE customer_id = ?;

If an index exists on (customer_id, total_amount), the DBMS can return results using only the index — there is no need to touch the table pages at all. Both columns the query asks for are already sitting in the index, in the order it needs them.

Indexes must be chosen to balance read speed against write cost. Write-heavy workloads generally need fewer indexes. Index monitoring tools can help identify unused or redundant ones.

08

Recovery Fundamentals

Recovery mechanisms ensure that a database remains consistent even when failures occur. They uphold the ACID properties — atomicity and durability above all.

Three mechanisms, each covering what the others cannot.

Copies of the database at a point in time, used for restoring data after media failure. They should be tested regularly to confirm they are usable — an untested backup is a hope, not a plan.

A record of every change the database intends to make, written before the change itself. The log is used to redo committed transactions and to undo incomplete ones.

The database writes its dirty pages to disk and records a checkpoint marking a known consistent state. This reduces how much log the system must scan during recovery — it need not look back past the last checkpoint.

Backups protect against physical storage loss. Logs let the database replay or reverse changes. Checkpoints bound how far back the system has to look. Lose any one of the three and some class of failure becomes unrecoverable.

09

Undo / Redo Strategies

Recovery methods differ depending on whether the DBMS writes changes to disk before or after a transaction commits. That one decision determines what the system has to clean up after a crash.

no-undo / redo

Deferred update

Changes are kept in memory until commit, so no uncommitted change ever reaches disk. On crash, only REDO is required — there is nothing on disk that should not be there.

undo / redo

Immediate update

Changes may be written to disk before commit, so the log must include both old and new values. On crash: undo the incomplete transactions, then redo the committed ones.

Example · crash recovery

log

L1: START T1
L2: WRITE T1: X <- 10 (old = 5)
L3: START T2
L4: WRITE T2: Y <- 20 (old = 0)
L5: COMMIT T1
CRASH

Recovery:
- Undo T2 → restore Y = 0
- Redo T1 → ensure X = 10 on disk

T1 committed, so its effect must survive — redo it to be sure X = 10 reached the disk. T2 never committed, so its effect must vanish — undo it using the old value the log recorded, restoring Y = 0. That is exactly why an immediate-update log stores the old value alongside the new one.

Logs must contain enough information to undo or redo operations correctly. Deferred update never needs UNDO, because uncommitted writes never reach disk; immediate update requires both.

Reflection: which method would be safer if the system crashes frequently? Which would be faster under normal operation? Notice that the answer is not the same for both questions.

10

Crash Scenarios and Recovery Workflow

Different types of failure require different recovery actions. Understanding how recovery uses logs and checkpoints explains how a DBMS restores consistency.

Failure What survived What recovery needs
Soft crash The disk is intact; the DBMS process stopped unexpectedly The log — undo the uncommitted, redo the committed
Media crash Nothing on that device; the storage itself failed The latest backup, plus every log entry written since it was taken

Soft crash recovery

  • Use the logs to identify which transactions committed.
  • Undo the uncommitted operations.
  • Redo the committed operations not yet written to disk.

Media crash recovery

  • Restore from the latest backup.
  • Replay the logs (REDO) from the backup point to the moment before the crash.

Example · log replay timeline

media crash

T0 (backup) ---- L1 ---- L2 ---- L3 ---- Crash

Recovery steps:
1. Restore backup taken at T0.
2. REDO log entries L1, L2, L3.
3. Database is restored to state at crash time.

Notice what this timeline demands: the logs have to survive the failure that destroyed the data. A backup and its logs stored on the same failed disk recover nothing — which is why log storage is kept separate, and why logs must not be deleted prematurely.

Soft crashes require UNDO and REDO based on commit status. Media failures require restoring a backup and replaying logs. Frequent checkpoints reduce how much log must be read during recovery.

11

Checklists

Everything above, reduced to what you would actually check when designing or operating a database.

index design

Before adding an index

Index the columns used frequently in filtering or joining. Use composite indexes when several columns are queried together. Drop unused or redundant indexes to save space and write cost. Balance read performance against write cost every time.

recovery

Before you need it

Maintain regular full backups. Ensure logs are stored safely and not deleted prematurely. Configure checkpoints to reduce recovery time. Test backup and restore procedures regularly — a restore first attempted during an outage is not a procedure.

The two lists pull in opposite directions on purpose. Indexing is about making the common case fast; recovery is about making the rare case survivable. A database that is only tuned for one of them will eventually disappoint you in the other.

Activity: Watching Indexes Work

A hands-on demonstration of how indexes change what the query planner does. Use the SQLite playground — Execute SQL Online — or your own local SQLite. Open it and clear any existing tables before you begin.

Step 1 · Set up the data

Copy and run the setup below. The dataset is deliberately large — 500 products and 10,000 sales — so that indexing effects are actually visible.

step 1 · ddl + sample data

CREATE TABLE Product(
    product_id INTEGER PRIMARY KEY,
    product_name TEXT,
    category TEXT,
    price INTEGER
);

-- Insert 500 products
WITH RECURSIVE c1(i) AS (
    SELECT 1 UNION ALL SELECT i+1 FROM c1 WHERE i <= 500)
INSERT INTO Product
SELECT
    i,
    'Item ' || i,
    CASE
        WHEN i % 3 = 0 THEN 'Electronics'
        WHEN i % 3 = 1 THEN 'Clothing'
        ELSE 'Sports'
    END,
    (i % 100) * 100
FROM c1;

CREATE TABLE Sales(
    sale_id INTEGER PRIMARY KEY,
    product_id INTEGER,
    quantity INTEGER,
    FOREIGN KEY(product_id) REFERENCES Product(product_id)
);

-- Insert 10,000 sales records
WITH RECURSIVE c2(x) AS (
    SELECT 1 UNION ALL SELECT x+1 FROM c2 WHERE x < 10000)
INSERT INTO Sales
SELECT
    x,
    (x % 500) + 1,   -- spreads sales across many product_ids
    (x % 5) + 1
FROM c2;

Step 2 · Filter without an index

Start with a selective filter and see how SQLite behaves.

SELECT *
FROM Product
WHERE category = 'Electronics'
  AND price > 8000;

Now check how SQLite executes it:

EXPLAIN QUERY PLAN
SELECT *
FROM Product
WHERE category = 'Electronics'
  AND price > 8000;

At this point you should still see SCAN TABLE Product.

Step 3 · Add an index and rerun

Write the CREATE INDEX statement yourself first — on the two columns the filter uses. Then compare.

After creating it, run the EXPLAIN QUERY PLAN again.

Look for: SEARCH TABLE Product USING INDEX idx_product_category_price.

Step 4 · Test a low-selectivity filter

Even with indexes, poorly selective columns may still cause table scans.

EXPLAIN QUERY PLAN
SELECT *
FROM Product
WHERE price <= 9000;

You may still see SCAN TABLE Product — price <= 9000 matches most of the table, so an index would cost more than it saves. The optimizer is not ignoring your index; it is declining it.

Step 5 · A composite index, matched by the query

Then run a query whose conditions match the index’s column order:

EXPLAIN QUERY PLAN
SELECT *
FROM Product
WHERE category = 'Electronics'
  AND price > 9000;

Step 6 · The join test

With 10,000 sales rows, the effect on a join is dramatic. First, the plan without a join index:

EXPLAIN QUERY PLAN
SELECT product_name, quantity
FROM Product JOIN Sales USING(product_id)
WHERE category = 'Electronics';

Now add an index on the join key and run it again.

Look for: SEARCH TABLE Sales USING INDEX idx_sales_product.

Step 7 · Transaction and rollback

Finally, a small demonstration of the recovery half of this lesson.

BEGIN TRANSACTION;
UPDATE Product SET price = price + 500 WHERE product_id = 10;
SELECT price FROM Product WHERE product_id = 10;
ROLLBACK;
SELECT price FROM Product WHERE product_id = 10;

The first SELECT shows the new price; the second, after the rollback, shows the original. The update was real inside the transaction and gone outside it — atomicity, in four statements.

What the activity demonstrates: index usage becomes clear when the table is large and the filter is selective; composite indexes work only when queries match their leftmost columns; joins on large tables improve dramatically with proper indexing; SQLite may still choose a table scan for low-selectivity columns; and transactions show how rollback protects consistency.

—

Summary

  • A DBMS spans storage tiers — RAM, SSD, HDD, tape — trading speed against cost and durability. Most operations are limited by I/O latency.
  • I/O cost is seek time, rotational latency, and transfer time; sequential reads are far more efficient than random ones.
  • The buffer pool caches pages in RAM, so a query that finds its page there avoids the disk entirely.
  • An index locates rows without scanning the table. B-trees handle equality and ranges; hash indexes handle equality only; composite indexes follow the leftmost-prefix rule; clustered indexes set physical row order; covering indexes answer a query by themselves.
  • Index a column that is frequently filtered or joined, has high cardinality, and sits in a table large enough that scans are expensive. Avoid indexing small tables, low-cardinality columns, and heavily updated columns.
  • Indexes cost storage, write time, and CPU. Every insert, update, and delete must maintain every relevant index — so write-heavy workloads want fewer of them.
  • Recovery rests on three mechanisms: backups against media loss, transaction logs to redo and undo changes, and checkpoints to bound how far back recovery must read.
  • Deferred update (NO-UNDO / REDO) keeps changes in memory until commit, so only REDO is needed. Immediate update (UNDO / REDO) may write before commit, so the log stores old and new values and recovery does both.
  • A soft crash leaves the disk intact: undo the uncommitted, redo the committed. A media crash destroys the data: restore the latest backup, then replay the log forward to the moment of the crash.
