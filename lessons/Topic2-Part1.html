01

Introduction

In this lesson, we will study models used to design databases. These models are very important as they let you plan/design your database, foresee potential problems (that can save you lots of headaches), and communicate about your DB with other stakeholders such as other DB admins, the programmer who will use your DB, and product owners who give you the requirements.

By the end of this lesson, you should be able to:

  • Identify and define entities, attributes, relationships, and keys in a given scenario;
  • Draw a basic Entity-Relationship Diagram (ERD) using standard notation;
  • Interpret ER diagrams and explain common cardinality and participation rules; and
  • Convert an ER diagram into a relational schema — that last one is Part 2’s job. This lesson gets you everything leading up to it.

02

Levels of a Data Model

Definition

A data model is a formal way to describe how data is organized, structured, and related within a system — a blueprint for how information is represented, connected, and managed in a database.

  • Sets the foundation for databases that are clear, consistent, and aligned with real-world needs.
  • Standardizes how data is stored and shared — promoting accuracy and reducing redundancy.
  • Data modeling answers three questions: what data do we store, how are pieces of data related, and what rules apply to that data?

Three levels, hiding different concerns

Where this lesson lives

Conceptual

Close to how people naturally perceive data. Focuses on what matters — the big picture of entities and relationships. Avoids implementation detail entirely. Example: the Entity-Relationship model.

Logical

Still understandable to people, but closer to how data sits in a computer — adds attributes, keys, and precise relationships. Still independent of any specific DBMS. Examples: Relational, Network, Hierarchical models.

Physical

Specifies how data is actually stored and managed — file structures, indexing, data types, specific to a DBMS platform. Examples: SQL-specific tables, indexes, partitions.

The trickiest distinction is Logical vs. Physical — Logical already looks like storage, but it still hasn’t committed to a DBMS.

03

The Entity-Relationship Model

Developed by Peter Chen in 1976 to provide a simple, understandable way to represent the structure and logic of a database — identifying which entities belong in it, and how those entities relate to one another.

ER Model = Entities + Relationships

  • Entities — the real-world objects or concepts represented in the database.
  • Relationships — the associations or interactions between entities.

Attributes — the properties that describe an entity — are the third piece of the picture. Page 5 covers those.

Chen, Peter Pin-Shan. “The entity-relationship model—toward a unified view of data.” ACM Transactions on Database Systems (TODS) 1.1 (1976): 9–36.

05

Definitions

Entity

An object with a physical existence — a particular person, car, house, or employee — or a conceptual existence, like a company, a job, or a university course.

Entity set

A collection or group of entities that share the same properties or attributes in a database or data model.

Attributes

The properties that define the entity type — the data that needs to be stored for each entity. In a database table, attributes are the columns.

08

Choosing Attributes of Entities

An entity’s attribute must:

  • Be directly linked to the entity.
  • Not be influenced by time — store birthdate, not age.
  • Not be influenced by other entities — number of siblings shouldn’t be an attribute if it can be counted from the database instead.
  • Avoid data redundancy.

If you can compute it from something else already in the database, don’t store it separately.

09

Types of Keys

A unique identifier for each record in a table. No two rows share it, and it can never be NULL. Example: in a Student table, Student_ID.

Any attribute, or set of attributes, that could qualify as the primary key. There can be several — only one gets chosen. Example: Student_ID and Student_Email might both be unique; both are candidate keys, even though only one becomes primary.

Two or more attributes that together uniquely identify a record, used when no single attribute is enough. Example: in an Enrollment table, neither Student_ID nor Course_ID alone is unique — together, they are.

An attribute in one table that links to the primary key of another, establishing the relationship between the two. Example: Enrollment.Student_ID references Student.Student_ID, so every enrollment corresponds to a real student.

10

Relationships

Definition

A relationship type represents the association between entity types. “Enrolled in,” for example, is a relationship type between the entity types Student and Course. In an ER diagram, it’s drawn as a diamond connecting the two entities with lines.

13

Participation Constraint

Total participation

Every entity in the set must participate in the relationship. If every student must enroll in a course, Student’s participation is total.

Partial participation

An entity in the set may or may not participate. If some courses have no students enrolled yet, Course’s participation in that same relationship is partial.

14

How to Draw an ER Diagram

Analyze the domain to find every distinct object or concept (e.g., Student, Course, Department). Represent each entity as a rectangle. Keep entity names clear, concise, and meaningful.

Determine how entities interact (e.g., Student enrolls in Course). Represent each relationship as a diamond between the related entities, labeled with a verb phrase. Never connect a relationship directly to another relationship — only to entities.

Represent attributes as ovals connected by straight lines. Underline key attributes. Mark multivalued, derived, and composite attributes with their proper notation.

Specify cardinality (1:1, 1:N, M:N) on each side of a relationship. Indicate total or partial participation with double or single lines.

Walk through the diagram against the original scenario. Check that every rule you were given is actually represented before moving on to a relational schema.

—

Summary

  • A data model is a blueprint for how information is organized, structured, and related.
  • Data models exist at three levels: conceptual (the ER model), logical, and physical.
  • The ER model is built from entities and relationships, drawn with rectangles, ellipses, and diamonds.
  • Entities can be strong (self-sufficient) or weak (dependent, with a partial key).
  • Attributes can be key, composite, multivalued, or derived.
  • Keys come in four flavors: primary, candidate, composite, and foreign.
  • Relationships have a degree (unary, binary, ternary, n-ary), a cardinality (1:1, 1:N, N:1), and a participation constraint (total or partial).
